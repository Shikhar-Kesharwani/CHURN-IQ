# CHURN-12 — Data dictionary and findings

**Jira:** CHURN-12 (E1; assignee Shimon Sarin). Evidence prepared by Aryan Gupta for the Sprint 3 closeout, with AI-assisted development tools.
**Dataset:** `backend/ott_churn_dataset.csv`, 5,001 rows × 22 columns, git blob `1975eeab8c4dfc8f75a3da5a20c010e11612c564` (`main` @ `074ec94`).
**Reproduce:** `python docs/analytics/recompute_analytics.py`. The `quality` and `observed_findings` sections of [`../analytics/results/recomputed_values.json`](../analytics/results/recomputed_values.json) hold every number quoted below.

## 1. About the data

* **The dataset is fully synthetic.** It was generated by `churniq_ml_pipeline.generate_dataset` (seed 42, 5,000 customers). `backend/add_emails.py` then added an `email` column and one demo customer, **CUST99999**.
* **The churn label comes from a known formula.** It is sampled from a probability built from a scoring formula with random noise, so there are no real customers, no real behaviour and no real outcomes.
* **The findings below are descriptive associations inside synthetic data.** They are not causal, and they are not evidence about real OTT subscribers.
* **Names and emails are generated, but look realistic.** This document deliberately does not reproduce any of them.

## 2. Column roles

| Role | Meaning | Columns |
|---|---|---|
| **Identifier** | Identifies a row and never reaches the model (`churniq_core.ID_COLS`) | `customer_id` |
| **Contact (personal-looking)** | Identifier columns that look like personal data; never a model input; do not copy into reports | `name`, `email` |
| **Feature** | Model input, after encoding (`churniq_core.encode_features`) | 15 columns, from `age` to `support_tickets` in the table below |
| **Generator-side (leakage)** | Computed from the generator's own churn probability, so they leak the label (`churniq_core.LEAKAGE_COLS`); never model inputs | `churn_probability`, `clv_score`, `clv_segment` |
| **Target** | Observed outcome the model learns (`churniq_core.TARGET_COL`) | `churn` |

**Engineered features.** `encode_features` adds four more features: `engagement_score`, `friction_score`, `is_new_customer` and `inactivity_flag`, along with one-hot columns. They are computed at runtime and are not columns in the file.

**Demo row (CUST99999).** It was added by `add_emails.py` with hand-set generator values: `churn_probability` 0.96, `clv_score` 500, `churn` 1. The serving artifact scores it with the real model instead (`prediction_source = demo`; see CHURN-38).

## 4. Generator fields vs model outputs

These columns have similar names but different sources, so they must not be confused.

| Raw dataset (generator-side) | Serving artifact `backend/customer_predictions.csv` (model) |
|---|---|
| `churn_probability`: the generator's true probability | `churn_prob`: production XGBoost prediction (hold-out, out-of-fold or demo) |
| `clv_score`: CLV from the generator probability | `clv_score`: CLV from the model `churn_prob` (same formula) |
| `clv_segment`: tier of the generator CLV | not stored; the API recomputes it from the model CLV with `churniq_core.get_clv_segment` |
| `churn`: observed outcome | `actual_churn`: a copy of `churn`, for evaluation only |

The two probabilities are correlated (Pearson 0.898) but not equal.

* **Every API and dashboard figure uses the model fields.** The current model-CLV tiers are High 1,241 / Medium 1,635 / Low 2,125; the generator tiers are 1,268 / 1,593 / 2,140.
* See [`../analytics/DASHBOARD_ANALYTICS_VALIDATION.md`](../analytics/DASHBOARD_ANALYTICS_VALIDATION.md) for details.

## 6. Findings: observed churn (the `churn` column, all 5,001 rows)

These are **observed synthetic outcomes**, not model predictions. For the model's predicted rates by segment, see the dashboard validation document.

* **Overall:** 2,155 of 5,001 churned, **43.1%**.

| Dimension | Group (customers) | Observed churn |
|---|---|---|
| Plan | Basic (2,226) / Standard (1,795) / Premium (980) | 43.9% / 43.6% / 40.2% |
| Device | Mobile (1,292) / Laptop (1,286) / Smart TV (1,216) / Tablet (1,207) | 45.5% / 39.7% / 43.6% / 43.6% |
| Tenure | 0–5 months (433) / 6–24 months (2,629) / 25+ months (1,939) | **65.4%** / 46.5% / 33.5% |
| Watch time per week | < 2 h (1,019) / 2 to < 5 h (1,191) / 5+ h (2,791) | **71.8%** / 42.8% / 32.7% |
| Payment failures, last 3 months | 0 (3,001) / 1 (996) / 2 (498) / 3 (350) / 4 (156) | 35.0% / 45.5% / 54.0% / 74.0% / **80.1%** |
| Support tickets | 0 (2,527) / 1 (1,237) / 2 (610) / 3 (354) / 4 (181) / 5 (92) | 36.9% / 43.6% / 48.4% / 58.2% / 60.2% / **80.4%** |

**Interpretation:**

1. **Engagement and tenure show the largest differences.**
   * Customers watching under 2 h a week churn at 71.8%, against 32.7% at 5 h or more.
   * New customers (0–5 months) churn at 65.4%, against 33.5% after two years.
2. **Payment and support friction rise steadily** with each extra failure or ticket.
   * The top groups are small: 4 payment failures has n = 156, and **5 tickets has n = 92**. Treat those rates with caution.
3. **Plan and device differ only slightly** (about 4 to 6 points).
   * In the generator, they matter only through a Basic + Mobile interaction, which fits that small difference.
   * Device and plan differences should not be over-interpreted.
4. **These patterns mirror the generator's scoring formula** (low watch time, few logins, long absence, payment failures, tickets and short tenure all add to the score). They describe how the synthetic data was built. They do not show what causes real churn.
